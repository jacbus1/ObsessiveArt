# Obsidian＋Miro＋Heptabase：三合一系統深度研究

**查核截至：2026-09-15。研究與架構提案；不是已完成應用程式。**  
文內來源代號對照 [SOURCES.md](SOURCES.md)。官方產品說明、授權原文及技術文件已作資料查核；沒有實際操作三款產品、執行元件、測試效能或讀取使用者匯出檔。

## 1. 結論：整合資料與工作流，不是拼接三個介面

建議把 Heptabase 式研究工作流放在產品中央，把 Obsidian 式資料可攜性和知識關聯當作底層原則，再加入 Miro 式白板操作。三合一的意思是同一批知識可以寫成文章、放到白板推敲、轉成圖譜探索，不是三套 app 的套殼。

主要工作流應是：收集來源 → 閱讀與摘錄 → 寫成自己的筆記 → 同一筆記在多個研究白板重用 → 建立有類型的知識關係 → 整理成輸出。AI 是可替換的輔助，而非開啟核心功能的必要條件。

第一個正式版本建議明確限制為「可自架的個人／小團隊知識工作台」，不要同時承諾完整 Miro 企業套件、完整 Obsidian 插件相容及完全取代 Heptabase。

## 2. 三者實際定位與目前重疊

| 產品 | 已查核的核心能力 | 對新系統的意義 |
|---|---|---|
| Obsidian | 本地 Markdown、Canvas，以及核心 Bases 的資料庫式視圖 | 開放資料與檔案思維；不能假設它只有文字筆記 |
| Miro | 白板內的多種物件，以及服務內的 SDK／API 擴充 | 學習空間操作；SDK 不是可以搬到自己網站的整套 Miro |
| Heptabase | 筆記／素材卡、同一卡片跨白板、研究、協作和 AI | 以知識卡片與研究脈絡設計產品，而非只做便利貼 |

Obsidian 的筆記原本就是本地 Markdown；Bases 以檔案及 properties 為資料來源。其官方 shared-vault 文件同時說明：目前不是同一檔案的即時協同編輯，也沒有細粒度權限。[S01–S04]

Heptabase 的官方模型明確把卡片與白板分開：白板不擁有卡片，同一張卡可以出現在多個白板。這是本案最值得借鑑的概念，而不是只模仿白色卡片的外觀。[S07]

截至查核日，Heptabase 已有協作、AI、CLI／MCP；官方 roadmap 最近更新為 2026-09-14。不能以「加入 AI」當作唯一差異化。該頁仍把 mini map 放在內部測試項目，不能當作已正式推出。[S08–S11]

Miro 的 SDK 用來擴充 Miro 環境，API 也不是所有原生物件的完整鏡像。其官方說明提及即時協作需要網路及手機離線檢視，不應把它簡化成「完全不能離線」，也不能反向假設全平台皆可完整離線編輯。[S14–S17]

## 3. 值得開發的差異化

第一是資料與畫面分離。筆記不是白板上的貼圖；同一張筆記在文章模式、卡片模式和圖譜模式維持相同身份。更新內容影響所有引用；移動位置只影響當前白板。

第二是可追溯研究。每個摘錄保留原文、來源檔案版本、頁碼或其他定位；自己的解釋與 AI 生成內容另行標記。支援「這個結論根據哪一頁？」「哪些卡片只是推測？」而非只有漂亮連線。

第三是資料出口和自架選擇。提供可讀的 Markdown／JSON Canvas 輸出，同時提供能保留完整結構的原生備份。使用者可以不用雲端 AI、可以另行部署同步服務，原始碼與私人資料分開管理。

第四是白板與圖譜的分工。白板是人手安排的論證與流程；圖譜是根據引用或關係生成的探索視圖。自動整理圖譜，不得洗掉使用者仔細排好的白板。

## 4. 使用介面與功能範圍

桌面端建議左側是工作區、筆記庫與搜尋，中間是文章／白板／圖譜切換，右側是來源、反向連結、卡片所在白板及 AI 提案。保留命令搜尋、分頁與返回上下文，不必把每個功能做成獨立 app。

| 能力 | 首個正式範圍 | 暫不承諾 |
|---|---|---|
| 筆記 | 區塊編輯、Markdown 匯入匯出、內部連結、標籤、屬性、歷史及垃圾桶 | 所有 Obsidian 插件與語法完全相容 |
| 白板 | 平移縮放、框選、拖拉、調整大小、對齊、群組／區段、卡片、文字、形狀、箭頭、基本手繪 | Miro 全部企業元件和應用市場 |
| 研究 | PDF 閱讀、高亮、來源定位、跨白板重用、章節／子白板整理 | 任意付費網站解析、完美 OCR、所有影片來源 |
| 圖譜 | 全域／局部圖、關係類型、標籤及來源篩選、節點定位 | 未測試的十萬節點流暢效能 |
| 多裝置 | 瀏覽器離線編輯、同步狀態、手機專用閱讀和整理流程 | 瀏覽器快取永不遺失，或原生桌面檔案同步已完成 |
| 小團隊 | 工作區 owner/editor/viewer、即時編輯、備份還原 | 任意跨工作區卡片分享、企業 SSO／稽核合規認證 |

手機應以快速收集、搜尋、單卡閱讀／編輯與白板概覽為主；觸控移動和編輯分模式。桌面縮小版不等於手機版。中文輸入法、軟鍵盤、縮放時字體清晰度、誤觸拖拉與重新開啟離線內容都要測試。

## 5. 統一資料模型：必須先定，再畫 UI

| 實體 | 儲存什麼 | 不應混入什麼 |
|---|---|---|
| Note／Block | 穩定 ID、內容、標籤、屬性、段落身份 | 某一白板專屬的座標 |
| Board | 白板身份、設定、區段和排列結構 | 重複的全文筆記副本 |
| Placement | noteId、boardId、位置、大小、折疊與外觀 | 另一份可獨立修改的筆記正文 |
| BoardConnector | 物件間的端點、箭頭和幾何路徑 | 自動被當作已證實的知識關係 |
| KnowledgeRelation | 來源／目標身份、關係類型、證據、人工或 AI 狀態 | 純粹美觀用的排版線 |
| Source／Annotation | 原檔 hash、版本、頁碼、區域、摘錄與定位狀態 | 沒有依據的來源標記 |
| Revision／ChangeSet | 操作身份、變更、可恢復歷史、同步收據 | 使用者密鑰或完整敏感日誌 |

例如「PCA」筆記同時放在「線性代數」及「降維比較」白板。改正筆記中的一段說明，兩邊都更新；移動「線性代數」上的卡片，不影響另一白板；只刪除一個 placement，不刪除筆記。複製成獨立筆記必須是另一個明確命令。

關係也要分清楚。「連到下一步」可能只是流程箭頭；「支持這個結論」才是需要證據的語義關係。AI 建議的連線不應默認成為人工確認的事實。

標題與路徑不是主鍵。中文同名筆記、檔案移動、別名、外部檔案重新命名都應由 ID 和匯入對照表處理。反向連結、全文搜尋及圖譜是可重建的索引，不是第二套內容來源。

## 6. 開源元件與授權選型

公開 repo 不等於所有程式都可按同一授權使用。Obsidian、Miro 和 Heptabase 的產品體驗可以作為功能研究對象，不能把原有品牌、付費介面資產或實作當成可直接合併的開源素材。[S05,S12,S14]

| 選項 | 本輪判斷 | 必須知道的限制 |
|---|---|---|
| AFFiNE | 最值得作成熟度對照與短期探索的完整產品候選 | 根 LICENSE 對 backend/common/native 有另行授權；不可把整個 repo 當成 MIT [S18,S19] |
| BlockSuite | 文件＋無邊界編輯器共用模型，值得做技術比較 | 本輪查到的獨立 repo 為 MPL-2.0；實際採用的套件／版本須逐一確認 [S20] |
| tldraw | 要快速建立成熟畫布，可評估正式商業授權 | SDK 預設條款只允許開發，production 需要適用授權；不是免費 MIT 核心 [S21] |
| React Flow | 適合流程圖與節點介面 | 官方明確不是完整通用白板引擎；不應只靠它宣稱完成 Miro [S22] |
| Excalidraw | 適合選配手繪／草圖模組 | MIT 不代表打包即有 hosted 版本全部協作能力 [S23,S24] |
| Tiptap | 推薦的筆記編輯器候選 | 核心及付費擴充要分開；Markdown 官方仍標 Beta，不能假設完整 Obsidian 無損往返 [S25,S26] |
| Konva | 推薦作自行控制空間編輯器的底層候選 | 提供繪製基礎，不提供整個產品；HTML 覆蓋層不會自動出現在 canvas 匯出 [S27,S28] |
| Sigma.js | 推薦作獨立圖譜 renderer 候選 | 不應接管白板內容或筆記權威資料 [S30] |

建議採「自有資料模型＋可替換開源元件」。代價是選取、吸附、群組、觸控、Undo、匯出及效能仍要自行整合。這個選擇偏向長期自主，不代表開發量最少。

保留兩個技術驗證候選：自建 Tiptap＋Konva 路線，以及 BlockSuite 的共享編輯模型。若後者在中文編輯、移動端、Markdown 往返與授權條件上明顯更適合，應在驗證後調整，而不是先被某個框架綁死。

## 7. 建議架構與權威資料的取捨

建議前端 React／TypeScript；筆記編輯以 Tiptap 作候選，白板以 Konva 加可控的文字編輯覆蓋層，圖譜以 Sigma.js／Graphology。同步評估 Yjs／Hocuspocus，瀏覽器持久化採 IndexedDB。後端保存身分／權限、持久更新與索引，使用 PostgreSQL；附件經儲存介面放在持久磁碟或 S3 相容服務；匯入、解析與匯出交由背景工作程序。這是待驗證的組合，不是已跑通架構。[S25,S27,S30–S34]

最重要的產品取捨是：本輪建議「結構化文件／CRDT 是 app 內的權威編輯狀態，Markdown 與 JSON Canvas 是對外交換投影」。不要同時宣稱外部 .md、編輯器 JSON、資料庫文字都能各自作唯一真相。

這不等於 Obsidian 原生檔案 vault。若必須任意外部編輯器直接改同一批檔案並同步回來，要另外做桌面檔案橋接、版本對照和三方合併；不能監聽檔案後直接覆蓋正在協作的文件。未知的富文字區塊要保留 sidecar 或標記降級，不可默默刪除。[S01,S06,S26]

每張筆記及每個白板分別建立同步文件，避免把整個工作區塞進一份巨型文件。跨筆記／白板的操作使用唯一命令 ID、持久工作紀錄與補償機制；單份文件能合併，不代表跨文件操作自動具有原子性。

UI 應明確區分：只存於本機、等待同步、伺服器已持久確認、權限阻擋／需處理衝突。網路已連上不是備份已完成，伺服器收過訊息也不等於磁碟已寫入。這些狀態都需要真正的 crash／reconnect 測試。

## 8. 離線、協作及權限

Yjs 的官方文件描述 IndexedDB 與網路 provider 的組合；Hocuspocus 提供認證／連線鉤子。但服務本身的成員權限、撤權、磁碟確認、垃圾桶與備份，都仍是本系統的責任。[S31–S33]

瀏覽器的 IndexedDB／其他儲存不應被包裝成永不遺失的 vault。低儲存空間、使用者清除資料或私密瀏覽，都可能影響持久性；申請 persistent storage 也不能取代可還原備份。[S35]

首版建議用工作區作權限邊界，owner/editor/viewer 三種角色，拒絕跨工作區直接引用。逐卡片跨團隊分享另作後續功能。這可以避免一張私人卡片因為被拖到另一白板而意外公開。後續若做公開分享，必須對被引用筆記、縮圖、附件、反向連結、搜尋及 AI 上下文分別檢查權限。

離線裝置已下載的資料不能靠雲端撤權神奇收回。需要清楚說明快取風險，企業級遠端抹除不是此版本承諾。傳輸加密、磁碟加密亦不是端對端加密；若之後做 E2EE，還要設計金鑰分享／恢復，以及對雲端搜尋和 AI 的影響。

## 9. 匯入／匯出：相容層不是拍照還原

| 來源 | 優先支援 | 必須報告的限制 |
|---|---|---|
| Obsidian | .md、屬性、wikilinks、相對附件及 .canvas 的支援子集 | 插件自訂行為、未知語法、重複標題及無法解析引用 |
| Miro | 合法授權 API／匯出中實際提供的物件、座標、文字、附件和連線 | 未公開物件、丟失互動語義；PNG／PDF 只能作參考，不是可編輯原始白板 |
| Heptabase | 官方支援匯出及 CLI／MCP 能讀取的卡片、白板、屬性 | CLI 的 PDF 摘錄不提供原始 PDF ID／頁碼／區域錨點，需要完整帳戶匯出才可保留 |
| 原生備份 | 穩定 ID、內容、位置、關係、來源與檔案 hash | 權限身分映射需重新確認，不能攜帶 secrets 或自動公開 |

Miro 的 API／SDK 本身並不涵蓋所有原生物件，因此遷移工具必須有 unsupported-items report。[S15,S16] Heptabase CLI 的來源定位限制是官方明確寫出的，不能只讀到高亮文字就聲稱「完整研究脈絡已遷移」。[S09]

JSON Canvas 1.0 很適合作為交換格式，包含 text/file/link/group 節點及連線，但不是整個 app 的權限、歷史、同步與 PDF 錨點格式。原生備份需要 versioned manifest、內容／白板／關係資料、附件 hash 和驗證報告；開放格式輸出提供可讀降級及附加 metadata。[S06]

## 10. 大白板、手機及匯出效能

你的參考畫面非常密集，所以效能應從模型與渲染方式開始設計，而不是等卡頓後才加快取。低縮放顯示摘要，中倍率顯示輕量卡片，只有正在編輯的卡片建立完整編輯器。只繪製可見範圍及少量預載區域，圖譜的標籤也應按縮放及篩選顯示。[S29]

圖像圖層與 HTML 文字層必須共用同一座標變換，否則縮放後點擊位置、選框和游標會偏移。尤其 Konva 明確不把 DOM portal 包含在 canvas 匯出中，因此 PDF／圖片輸出應有獨立的場景 renderer，不能只呼叫 toDataURL 然後宣稱整張筆記白板已完整輸出。[S28]

建議第一輪驗證目標：一萬張筆記的指定查詢集、桌面一千個混合物件白板、手機二百五十個物件場景、十名協作者。這些是**測試負載提案，並非已達成的效能**；硬體、瀏覽器、網路、檔案大小及判定門檻必須隨結果一起記錄。

## 11. AI 接入應該做什麼

AI 最有價值的動作是：從選定來源提取概念卡、建議有證據的關係、發現未支持的論點、把已選卡片整理成章節，以及提出白板布局變更。每次寫入先提供預覽和差異，使用者批准後才成為正式內容；模型建議與人工確認分開標記。

Heptabase 本身已經具備來源導向的 AI 工作流，因此本案的改進目標應是可替換 provider、可檢查依據及可審核的變更，而不是只多一個聊天框。[S10]

Provider key 不進前端 bundle，不把任何第三方登入 cookie 當作一般 API。研究素材是不可信輸入，不可憑 PDF／網頁中的指示執行系統命令、導出整個私人工作區或擴大權限。核心筆記／白板功能在未設定 AI 時仍應正常使用。

## 12. Production-ready 的驗收標準

| 方面 | 必須拿出實際證據 |
|---|---|
| 資料一致性 | 一張筆記跨白板更新、改名不斷鏈、刪位置不刪內容、原生備份還原後 ID／來源仍成立 |
| 同步可靠性 | 斷線重連、重複及亂序訊息、程序突然中止、多人修改後收斂；不得丟失已確認持久的操作 |
| 權限 | API、WebSocket、附件、搜尋及匯出全部服務端檢查；viewer 不能靠修改 request 寫入 |
| 安全 | 匯入 HTML 淨化、Zip 路徑／大小限制、URL 抓取 SSRF 防護、session／origin／訊息大小控制 |
| 可恢復性 | 在獨立環境完成資料庫與附件一致的還原，核對 hash；migration 有備份及回復程序 |
| 端到端使用 | 中英輸入法、鍵盤、觸控、離線重開、錯誤與衝突提示，以及完整匯出可讀性 |
| 維護發布 | 套件固定版本、第三方 notices、SBOM、CI、健康檢查、可觀測性、版本與事故處理文件 |

WebSocket 與遠端 URL 匯入的具體攻擊面參考 OWASP 官方指引；勾選清單不能代替測試。[S37,S38] 功能測試、匯入往返、備份還原與所有效能測試在本輪均未執行。

## 13. GitHub、部署與實作順序

GitHub repo 用來放原始碼和測試，不是放工作區資料；GitHub Pages 是靜態主機，不會代替本案的同步服務、API 和資料庫。完整自架版需要另外運行持久化服務，正式環境還需要 TLS、備份、更新與監控。[S36]

建議另開獨立 repo、從私人分支開始，英文 README 與繁體中文 README 分開。首個實作里程碑必須是垂直切片：建立筆記 → 同時出現在文章／白板／圖譜 → 編輯同步 → 關閉重開 → 匯出 → 在全新空間還原。先證明這條路，再補大量工具列。

接著才加入 PDF 錨點、更多白板操作、工作區權限、即時協作和手機打磨，最後通過還原、權限、斷線、故障與效能驗收。各階段的完成標準要以測試證據為準，不以功能名稱數量為準。

若以兩至三名熟悉相關技術的工程師加 QA 規劃，自架小團隊版本可先用十二至二十週作粗略排程假設；這是可重估的規劃，不是已知工期或交付承諾。若要求完整檔案雙向同步、逐卡片跨團隊分享和企業級能力，需另行擴大範圍。
